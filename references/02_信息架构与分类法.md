# 02 · 信息架构与分类法：怎么把东西放对地方

> 分类错了，后面检索全废。本文件给一套可落地的分类 + 标签 + 命名规范。

## 一、分类的两条路线

### 路线 A：树状分类（Taxonomy）
适合「边界清晰、彼此互斥」的信息。
- 例：产品文档 / 技术文档 / 运营文档 / 客服文档。
- 规则：**MECE**（Mutually Exclusive, Collectively Exhaustive）不重不漏。
- 层级：建议最多 3 层（一级大类 → 二级主题 → 条目），超过就难维护。

### 路线 B：标签网络（Folksonomy）
适合「跨类关联、一个东西属于多处」的信息。
- 例：一条「退款流程」既是「客服」又是「财务」又是「合规」。
- 规则：标签自由但需「受控词表」——先定一批规范标签，禁止随意造词。

### 实战组合：分类定大方向，标签做横向串联
- 每篇必属一个分类（唯一），可贴多个标签（多值）。
- 本 Skill 产出：`category`（唯一分类）+ `tags`（多值标签）。

## 二、MECE 拆分的五个维度（按需选一）

建分类树时，同一层必须用「同一个维度」切，否则会重叠：

1. **按对象**：用户 / 商户 / 内部员工。
2. **按生命周期**：售前 / 售中 / 售后。
3. **按职能**：产品 / 技术 / 运营 / 财务。
4. **按主题**：账号 / 计费 / 安全 / 数据。
5. **按形态**：指南 / 规范 / 案例 / 故障。

反例（混淆维度）：同时按「主题（安全）」和「生命周期（售后）」在同一层 → 会出现「售后安全」放哪都不对的尴尬。

## 三、标签规范（受控词表模板）

```
# 规范标签（示例，按你的业务改）
- 业务域：账号, 计费, 安全, 数据, 内容, 客服
- 文档型：FAQ, 教程, 规范, 案例, 故障, 变更
- 受众：新人, 用户, 运营, 研发, 管理
- 紧急度：常规, 重要, 紧急
```
规则：
- 标签用「名词」而非句子（用 `退款` 不用 `怎么退款`）。
- 单值标签长度 ≤ 6 字，便于检索与展示。
- 标签总数建议 ≤ 30 个规范词，超了就合并同类项。
- 禁止「其他 / 杂项」这种垃圾桶标签（真归不进就改分类）。

## 四、命名规范（条目标题）

好标题 = 能当检索词的标题。

| 差标题 | 好标题 | 理由 |
|---|---|---|
| 新的东西 | 2026 会员计费规则 | 含时间+主题，可检索 |
| 关于安全 | 用户数据加密与脱敏规范 | 动宾结构，一看就懂 |
| 问题 | 忘记密码如何重置 | 疑问式，匹配用户原话 |
| 第三版 | 退款流程 v3（2026-09） | 版本+时间，避免歧义 |

标题公式：`[对象] + [动作/主题] + [版本/时间（可选）]`
- 教程类：`如何/怎么 + 动作`（如何重置密码）
- 规范类：`对象 + 规范/标准`（数据脱敏规范）
- 案例类：`场景 + 结果`（大促宕机复盘）

## 五、分类冲突处理

- 一条信息两边都能放 → 选「用户最常检索的入口」分类，另一面用标签补。
- 分类树长得超出 3 层 → 说明该拆库了，不要硬塞。
- 历史分类想改名 → 用 `fingerprint` 追溯受影响条目，批量改，别手写漏。

## 六、与本 Skill 的衔接

脚本 `kb_chunk.py` 的 `category` 取自文档第一个 H1（顶层分类），`tags` 由标题路径 + 正文高频词 + 你给的 `--tags` 共同推导。你提供 `--tags 产品,帮助中心` 即注入受控词表，脚本不会乱造标签。
